# Persistent desktop voice

The browser hands-free hook is tied to the page and browser speech service. It previously disabled itself on network failures. It now retries transient failures with bounded backoff, but cannot promise listening after a browser suspends or unloads the page.

For Windows background use, enable **Desktop wake-word voice** once in the assistant. The existing Windows System.Speech bridge runs under the local ULTRON server, independently of browser focus, and uses the same parseVoicePlan, system/browser actions and approval tokens. Its opt-in is saved locally and restored on server start. No login task/service is installed: ULTRON must be running, and Windows must be awake. Disabling voice releases the microphone; say “Ultron stop listening” to disable by voice. Browser voice is disabled while desktop voice is enabled to avoid duplicate execution.

Say the wake word with every command: “Ultron open YouTube”, then “Ultron close YouTube and open VS Code”. Only ULTRON's managed browser is closed, never an unrelated YouTube tab. Up to five commands queue; a failed step stops the rest of that plan. “Ultron cancel” discards pending work, but cannot undo an operation already started. Ordinary commands are ignored during desktop spoken feedback to avoid echo, but the exact stop controls remain available. This is not speaker authentication: nearby people or media can trigger permitted commands.

App closing and Defender scans require on-screen approval. Voice cannot approve sensitive actions. An approval expires in 60 seconds even without a browser open. A Defender quick scan follows the existing Windows security policy and may quarantine threats; no security exclusions or protection settings are changed. Completion does not guarantee absence of malware.

Requires an installed English Windows speech recognizer and microphone permission for desktop apps. Failures retry with capped exponential backoff; after repeated failures, the panel explains how to retry. Recognition accuracy depends on microphone/noise/accent. Raw audio is not stored or uploaded by this bridge. Last 30 command/status events are kept in server memory.

The desktop recognizer keeps a high-priority fixed grammar for app actions, folders, browser controls, phone navigation, scan requests and stop controls. Up to six direct actions can be joined. `lib/voiceGrammar.json` adds fixed phrases and explicit dictation prefixes for file queries/paths, browser URLs/fields, phone input and agent goals. Dictation is accepted only after a wake word and a supported prefix; every resulting transcript must still pass the shared parser. There is no unrestricted shell/dictation executor. Both grammars retain the 0.65 confidence gate. Fixed commands still work if the installed recognizer cannot load dictation; the panel reports that limitation. Exact paths, URLs, text and numbers can be misheard. Type precision-sensitive values and inspect approvals rather than assuming correct transcription.

Run `npm run check:native-speech` for both fixed-command and prefixed-dictation synthetic-audio checks. They feed generated speech into the actual Windows recognizer without microphone access, audio playback or tool execution. Emitted transcripts must route through the shared parser, agent-goal router or stop-control classifier. These checks do not measure a user's microphone/accent accuracy or guarantee exact free-text transcription.

Desktop browser actions now retain the last observed snapshot. Approvals bind to that snapshot and the exact action; changed pages still require a fresh inspection. Android device selection is retained and included in approval-bound payloads. File results, document summaries, phone screenshots, browser element IDs and plan previews are available through **Latest voice result → View result**. Large results stay server-side until requested, rather than being retransmitted every status poll. Only the latest result is retained in process memory; no audio is stored.

Research/report/booking goals create a saved review-state task using the existing agent planner. The recognized goal and opted-in memory may be sent to the configured provider. No task tool runs automatically. Stop aborts in-progress planning and pauses active tasks; Stop Listening also cancels native planning while releasing recognition. General conversational questions remain in chat/browser voice. See [all supported commands](COMMANDS.md).

Validation: build/type checks and a local speech-engine startup check are not substitutes for real spoken-command tests. Check two successive wake-word commands while another window is foreground; test permission denial, stopping voice, and approval cancellation. Do not claim background recognition verified solely from parsing text.

## Microphone diagnostics

The panel exposes the Windows recognizer's input level (0–100), maximum observed level since listener startup, freshness, and reported signal problems such as TooSoft or TooNoisy. These counters come from the same audio input used for recognition, not a separate browser microphone. Readings pause during spoken feedback and are marked stale after five seconds without an update. No audio is recorded or uploaded. An input meter is not a calibrated sound-pressure or speech-quality measurement, and the lifetime peak can include noise.

If commands are rejected, inspect these diagnostics before restarting or changing the grammar again. Check Windows Sound Input, hardware mute, microphone distance and background noise. Keep the recognition confidence gate; do not force uncertain transcriptions into system actions. A zero-confidence empty candidate is displayed as unrecognized speech, not a meaningful command. Joined requests can repeat the wake word after “and”, for example “Ultron open YouTube and Ultron open the Notepad”.

References: https://learn.microsoft.com/en-us/dotnet/api/system.speech.recognition.speechrecognitionengine.recognizeasync?view=netframework-4.8.1 and https://learn.microsoft.com/en-us/powershell/module/defender/start-mpscan

## Stop versus Stop Listening

Both browser hands-free and Windows desktop voice require a final wake-word control phrase with an exact control ending. While speaking, busy, or within the short browser echo window, the browser can recognize a final “Ultron stop” or “Ultron stop listening” even if preceding speaker echo was bundled into the transcript. Extra words after the control ending do not match. Interim “Ultron stop” is not executed while it could still become “Ultron stop listening”. Recognition latency and microphone quality still apply; this is not a hardware emergency-stop system.

- **Ultron stop**: silently cancel desktop speech immediately upon recognition, clear queued steps/approvals, abort active provider requests and pause active agent tasks. The assistant page receives a push event to cancel browser speech/generation without waiting for the four-second status poll. The microphone remains enabled. No spoken acknowledgment is generated.
- **Ultron stop listening**: silently stop recognition and release its input, clear retry timers and queued commands, and persist desktop voice as disabled. Browser voice immediately aborts recognition, stops microphone tracks and closes its audio context. No restart occurs until manual enable in the interface. The app/server stays running. This command is not a request to terminate unrelated apps or undo completed actions.

Desktop output uses asynchronous synthesis so console control messages are not blocked by long utterances. Stop controls bypass speech-output echo suppression without lowering the confidence threshold. Headphones reduce feedback/self-trigger risks. Recognition accepts the full phrase; no fuzzy matching is used for these controls.

Browser hands-free filters text matching recent assistant output during playback and for 2.5 seconds afterward, including final transcripts delivered after synthesis ends. It checks explicit stop controls before filtering echo. This is best-effort transcript filtering, not speaker identification or an acoustic echo-cancellation guarantee. It can suppress deliberate immediate repetitions of the assistant's words; say the wake word with a different request when needed.

Push subscriptions use same-origin, loopback-only POST requests and are cleaned up on disconnect. Provider cancellation is server-side too, not just hiding streamed text. Already-started external effects (app launches, OS scans, navigation, approved closes) may finish; stopping cannot undo them or safely force-kill external processes.
